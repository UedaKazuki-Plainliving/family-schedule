## 1. システムの目的

家族メンバー（初期値：お父さん／お母さん／長女／次女／長男）が、
**「今日と明日、誰が何をするか」を最小操作で共有する**ことを目的とする。

時刻管理・通知などの高機能化はせず、**「ぱっと書いてぱっと見る」体験**を最優先する。

---

## 2. スコープ

### 2.1 含まれるもの（MVP）

- メンバーは最大10名まで登録・変更・削除可能（初期値5名）
- 「誰が」「いつ（日付）」「何を（フリーテキスト）」の3項目のみで予定を管理
- 今日と明日の予定を1画面で表示
- フリックによる前後の日への移動
- 予定の登録・編集・削除
- データはサーバー側 PostgreSQL に保存
- 画面はブラウザ（スマホ優先、PCも可）

### 2.2 含まれないもの（将来：バックログ）

- 時刻入力／時間帯
- 通知（LINE／メール）
- 繰り返し予定
- カテゴリ・色分け
- 認証・権限分離
- 過去の予定の集計・カレンダー表示

## 4. 非機能要件

| ID | 分類 | 要件 |
|----|------|------|
| NFR-01 | 性能 | スケジュール画面の表示は1秒以内（ローカル想定） |
| NFR-02 | 性能 | 予定の保存・更新・削除は500ms以内 |
| NFR-03 | ユーザビリティ | スマホ片手操作で完結する |
| NFR-04 | ユーザビリティ | 文字サイズはデフォルトで**16px以上**（スマホ不得手なユーザー配慮） |
| NFR-04' | ユーザビリティ | タップ可能領域は最低 **44×44px** を確保（誤タップ防止） |
| NFR-05 | 可搬性 | 画面はモダンブラウザ（Chrome/Safari/Edge 最新2バージョン）で動作する |
| NFR-06 | 保守性 | API・UI・DB を疎結合に分離（API中心の設計） |
| NFR-07 | 信頼性 | 同時編集の競合は想定外（家族規模なので）。最後の更新が勝つ |
| NFR-08 | セキュリティ | MVPでは家庭内LAN前提。認証は将来課題 |
| NFR-09 | テスト容易性 | API単体・E2Eの自動テストが回る |

## 5. データ要件

### 5.1 主要エンティティ

- **Member（家族メンバー）**：最大10名。マスタ（追加・変更・削除可）。
- **Schedule（予定）**：誰が／いつ／何を、を持つレコード。

### 5.2 メンバー定義（初期値）

初期データ（Flyway V1 で投入）。メンバー管理機能（FR-24）により変更可能。

| ID | 名前     | 表示順 |
|----|----------|--------|
| 1  | お父さん | 1      |
| 2  | お母さん | 2      |
| 3  | 長女     | 3      |
| 4  | 次女     | 4      |
| 5  | 長男     | 5      |

## 6. 制約条件

- 開発言語：**Java（Spring Boot 想定）**
- DB：**PostgreSQL**
- フロントエンド：HTML + 軽量JS（フレームワーク選定は設計時）
- 自動テスト：JUnit 5（単体）、Cucumber-JVM（BDD）、**Playwright for Java（API＋E2E）**
- 開発手法：アジャイル（小さな単位で要件→設計→TDD→検証を回す）

---

## 7. 受け入れ基準（サマリ）

- ペルソナ5人それぞれが、自分のユースケースを最後まで実行できる
- すべての BDD シナリオ（Gherkin）がパスする
- ペルソナレビューで「重大な要求不足」がゼロである（軽微なものはバックログ行き）
