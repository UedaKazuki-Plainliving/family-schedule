### BUG-VALIDATOR の一貫性

各仕様書における BUG-VALIDATOR の記述を以下に整理する。

| 仕様書 | テストID | 記述内容 |
|--------|---------|---------|
| ut-spec.md | UT-V-02 | `VALID_MEMBER_IDS = Set.of(1,2,3,4,5)` がハードコードされており、`memberId=6` がエラーになることを再現テストとして検証する。重大度: High、ステータス: 未修正 |
| it-spec.md | IT-S-11, IT-SC-02 | UT と同じ根本原因。IT-S-11 は API 単体で 400 を確認、IT-SC-02 はメンバー追加からのシナリオフローで FAIL を確認。合格対象外として記録 |

## 共通の欠落観点

4ファイルに共通して欠落または不足している重要なテスト観点を以下に列挙する。

### 欠落1: displayOrder の動的変更テスト

メンバーを追加・削除した後の `displayOrder` が正しく採番・再採番されるかを検証するテストが IT 以降のレベルに存在しない。UT-M-01 で `repository.save()` の呼び出しは確認しているが、保存されるエンティティの `displayOrder` 値が正しいかは検証されていない。

- **影響範囲**: IT-M-02（メンバー追加後の `displayOrder` 値が `6` であることは確認しているが、削除後の再採番は未確認）
- **推奨対応**: IT に「メンバーを削除した後に新メンバーを追加すると `displayOrder` が連番になること」のテストケースを追加すること

### 欠落2: 同一日付・同一メンバーへの重複予定登録

同一の `memberId` と `date` の組み合わせで複数件の予定を登録できるかどうか（許可する仕様か禁止する仕様か）のテストが UT/IT/ST いずれにも存在しない。要件定義書に明示があれば対応が必要。

- **影響範囲**: UT-S-01、IT-S-07 では1件登録のみ確認
- **推奨対応**: 重複登録が許可仕様であれば IT に確認テストを追加し、禁止仕様であれば UT に `ValidationException` のテストケースを追加すること

### 欠落3: インライン編集後の content が 100 文字を超える場合のエラー表示

ST-03-06 では予定追加モーダルでの 101 文字バリデーションを確認しているが、インライン編集（S-04）で 101 文字を入力した場合の動作（エラーメッセージの表示場所、保存のキャンセル等）を確認するテストが ST にも AT にも存在しない。

- **推奨対応**: ST に「ST-04-07: インライン編集で 101 文字入力後に Enter → エラー表示またはキャンセル」を追加すること

### 欠落4: API レスポンスの `deletedAt` フィールドの型確認

IT-S-07 の期待レスポンスに `"deletedAt":null` が含まれているが、論理削除後（IT-S-16）の `deleted_at` フィールドの値が ISO 8601 形式（`2026-04-26T00:00:00Z` 等）で返るかどうかを検証するテストがない。フロントエンドでの日時フォーマット処理に関わる重要な確認事項。

- **推奨対応**: IT-S-16 の DB 確認 SQL に加え、API レスポンスの `deletedAt` フィールドの型と形式（文字列 / null / ISO 8601）を確認するステップを追加すること

### 欠落5: AT における「テスト用端末の操作ガイド」

at-spec.md の 1.5 節に実施手順はあるが、実際に家族が操作する際の「最初の URL の開き方」（LINEで送ってもらう、QRコードを読む等）の具体的な手順がない。AT では非技術者が実施者であるため、この部分の欠落は実施前の混乱を招く可能性がある。

- **推奨対応**: AT 冒頭に「テスト開始の手順: LINEグループにURLを投稿し、各自のスマホで Safari/Chrome から開く。アプリストアのインストールは不要」等の1ページの案内を追加すること
