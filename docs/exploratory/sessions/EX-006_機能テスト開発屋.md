# EX-006：機能テスト開発屋（境界値・データフロー・ホワイトボックス）

| 項目 | 値 |
|---|---|
| ラウンド | 第2ラウンド |
| 担当 | 機能テスト開発屋 |
| 実施日 | 2026-04-26 |
| 観点 | 境界値・データフロー・ホワイトボックス |

## ミッション
> 実装コードの内部構造を踏まえ、バリデーション境界・DBスキーマとの整合性・並行処理パターンを探索し、単体テストでは検出できないデータフロー上の欠陥を発見する

---

## 探索の流れ

### ① 仮説：date フィールドは null チェックされていないのでは？

`ScheduleValidator` を見ると `content` の空チェックはあるが、`date` フィールドの null チェックが見当たらない。フロントは `<input type="date">` のブラウザ制約に依存しており、API を直叩きすれば date なしで登録できそうだ。

**手順**
```
POST /api/schedules
{"memberId": 1, "content": "テスト"}   ← date を省略
```

**発見 → ET-004**
201 で登録成功。DB に `date = NULL` が入り、画面表示時に `NullPointerException` が発生。バリデーターが date のチェックを持っていないことが確定。

---

### ② 仮説（ET-004 の発見から派生）：PUT（更新）でも同様の抜けがあるのでは？

CREATE 時のバリデーターが date をチェックしていないなら、UPDATE 時に呼ばれるバリデーターも同様の実装になっている可能性がある。さらに、バリデーターが **初期化時に静的なメンバーIDリストを固定保持**していれば、後から追加されたメンバーへの更新が弾かれるはずだ。

**手順**
1. 新しいメンバーを `POST /api/members` で追加
2. そのメンバーの予定を `POST /api/schedules` で登録（成功する）
3. 同じ予定を `PUT /api/schedules/{id}` で更新

**発見 → ET-012**
更新時に 400 が返る。`ScheduleValidator` がサービス起動時点のメンバーIDリストを保持しており、後から追加されたメンバーが「不正なメンバーID」として弾かれる。CREATE と PUT で同じバリデーターを使い回しているが、リストの更新タイミングが CREATE 時のみになっていた。

---

### ③ 仮説（ET-012 の発見から派生）：DB の列長制約はアプリバリデーターと合っているか？

バリデーターに整合性の問題があったなら、DB 側の DDL との整合性も怪しい。`V5__content_max_100.sql` を見ると `VARCHAR(100)` だが、アプリは `codePointCount <= 100` で判定している。絵文字（サロゲートペア）はコードポイント 1 でも UTF-16 code unit が 2 になるため、**アプリを通過した 100 絵文字が DB で拒否される**可能性がある。

**手順**
```
POST /api/schedules
{"memberId": 1, "date": "2026-04-26", "content": "😀".repeat(100)}
```
→ アプリバリデーター：codePointCount = 100 → 通過  
→ DB：VARCHAR(100) に 200 UTF-16 code units → 拒否

**発見 → ET-006**
500 INTERNAL。アプリを通過したリクエストが DB 層で落ちる。アプリと DB のカウント基準が異なることが根本原因。

---

### ④ 仮説（ET-006 の発見から派生）：MemberService の名前長チェックも同じ問題があるのでは？

`ScheduleValidator` は `codePointCount` を使っているが、`MemberService` の名前長チェックが `String.length()` のままであれば同じ問題が再現する。特に絵文字メンバー名を登録したときに上限計算がずれる。

**手順**
1. `MemberService.addMember()` のコードを確認 → `name.length()` を発見
2. 絵文字を含むメンバー名で上限付近のケースを投入

**発見 → ET-009**
`String.length()` 基準のため、サロゲートペア絵文字が 2 カウントされる。ユーザーが見た目 1 文字と感じる絵文字で制限に達してしまう。

---

### ⑤ 仮説：メンバーIDの採番ロジックに並行処理の問題はないか？

`MemberService` が `findMaxId() + 1` でIDを採番しているなら、複数リクエストが同時に来ると同じIDが採番されて PRIMARY KEY 重複が起きる。

**手順**
1. `MemberService.addMember()` の採番処理を確認 → `findMaxId() + 1` を発見
2. 同時に `POST /api/members` を 2 回送信

**発見 → ET-005**
2 リクエスト目が PRIMARY KEY 重複で 500 エラー。シーケンスを使えば DB 側でアトミックに採番されるため解決できる。

---
